## Browser acceptance and actual defect

- The initial real Chromium **320 CSS px** sign-in view failed due to horizontal overflow: `document.scrollWidth=333` at `clientWidth=320`. The `Library password` form's intrinsic input width prevented its centered grid card from shrinking inside the 320px document. Corrected `min-width:0` on the login card/input, `width:100%` on the input and `minmax(0,1fr)` on the form track. These are **layout-only** CSS corrections: no API/auth, encryption, password storage, collection metadata, photo file or native-client change.
- **After the correction**, real Chromium 159.0.8154.6, Firefox 159.0 and Linux WebKit 27.2 ran the development Photos **sign-in screen** at desktop 900×800 light, mobile 390×844 dark, and compact 320×760 light: **9/9 PASS**. Verified accessible `Library password`, keyboard Tab to `Unlock library`, correct inherited Iris accent, OS appearance, panel bounds, no page overflow, zero unexpected external requests, zero uncaught runtime errors. Button contrast is **6.86:1 light** and **8.05:1 dark**.
- Source/attribution and compact-layout regression tests run in the existing protected `web` CI job with the three other browser-independent Photos test families. Actual screenshots reviewed: [fixed 320px light layout](evidence/photos-chromium-compact-light.png) and [390px dark layout](evidence/photos-chromium-mobile-dark.png). Both show only an **empty local login screen** without personal photos, credentials or provider data.
- Reproduction: `cd web && npm ci --ignore-scripts && npm run dev -- --port 18751 --strictPort`; in another terminal from `web/`, set `GC_PLAYWRIGHT_CORE_MODULE`, `GC_CHROMIUM_BIN`, `GC_FIREFOX_BIN`, `GC_WEBKIT_BIN` to verified absolute existing files and run `npm run browser:acceptance`. The source-controlled opt-in runner performs no installations, no credential submission and no requests beyond the temporary loopback origin. Optional screenshot output uses a pre-existing absolute `GC_QA_SCREENSHOTS_DIR`.
